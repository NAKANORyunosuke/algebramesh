# ADR 0016: ジョブの期限は結果の検算まで含む

- 状態: 採用
- 日付: 2026-11-05
- 関連: [ADR 0003](0003-result-check-and-deadlines.md), Issue #9

## 背景

ADR 0003 は, 検算を CAS の呼び出しと同じ締切 (ジョブ開始からの `wall_seconds`) の下に置くと決めた.
Asir backend はそうしていたが, Macaulay2 と OSCAR の backend は CAS の driver の完了までにしか期限を掛けず, 結果の変換と検算 (`spawn_blocking`) を期限なしで待っていた.
そのため `wall_seconds = 10` のジョブで CAS が 9.9 秒で答え, 検算に数十秒掛かっても `SUCCEEDED` になりえた.
また各 backend が `timeout` からそれぞれ締切を計算していたので, 段階ごとに時間が数え直されることがあった.

## 決定

- `wall_seconds` は, ジョブの実行全体の壁時計時間とする. CAS の起動または借り出し, 計算, 応答の受信と decode, 結果の変換と検算をすべて含む.
- 締切は, 共通の実行処理 (`algebramesh_core::execute`) がジョブの開始時に 1 回だけ決め, `ExecutionContext.deadline` で各段階に渡す. 各段階は残りの時間だけを使う (`ctx.expired()`, `ctx.timed_out()`). driver の起動 (`run_driver`), OSCAR の借り出しと問い合わせ, Asir のセッションの開始と計算は, この締切を使う.
- 検算は `algebramesh_core::check::check_result` で行う. blocking thread で動かし, 締切か取り消しが来たら, 検算の終わりを待たずに `TIMEOUT` か `CANCELLED` を返す. 締切と同時に終わった検算も `TIMEOUT` とする.
- 締切の後に返った成功は `TIMEOUT` にする. 締切から 5 秒たっても返らない backend は, 共通の実行処理が待つのをやめて `TIMEOUT` を返す (driver のプロセスは `kill_on_drop` で止まる).
- 検算の失敗 (`UNSUPPORTED_RESULT`) と期限切れ (`TIMEOUT`) は区別する. 検算が終わっていない結果は `SUCCEEDED` にしない.

## blocking thread の資源

blocking thread は外から止められない. 期限を過ぎた検算が使い続ける資源には, 次の上限がある.

- 中断: 検算は `Interrupt::checkpoint` で中断の求めを確かめる. 因数分解の検算では因子ごと (冪の計算の前と積の前), GKZ の級数の検算では指数と解ごとに確かめ, 求められていれば次の区切りで止まる. 1 つの多項式の積の途中では止まらない. 因数分解の応答の変換では, 定数の因子の重複度乗を二乗の繰り返しで計算し, 冪の前と積の前に確かめる. 0, 1, -1 の冪には乗算をしない. 重複度が 2 以上の定数の因子から取る冪の bit 数には, 応答ごとに上限 (予算) を置き, 予算を超える冪を含む応答を拒む. 整数の冪の予算は, 入力の係数の分子の bit 数の最大値の 2 倍 (少なくとも 2^16 bit) とする. 分数の冪の予算は, 分子と分母の bit 数の合計で 2^16 bit とする. 予算の残りは因子の順序によらない. 重複度 1 の定数 (多項式の content など) には上限を置かず, 予算からも取らない (Issue #91). Macaulay2 は ZZ 上で content を素数の冪 (素数と重複度の組) で返す. content は入力の各係数の分子を割り, その素数の冪の bit 数の合計は content の bit 数の 2 倍以下なので, 正しい応答の素数の冪は整数の予算に収まる. 積では, 約分の gcd を, 大きい方を小さい方で 1 回割ってから取り, 積を約分し直さない. num-bigint の二進 gcd は, 一方が 1 でも他方の bit 数の二乗の時間がかかる (2^20 bit の整数と 1 の gcd で約 1.5 秒). BigRational の積は, 整数どうしでもこの gcd を 3 回 (最後は積について) 取るので, 2^20 bit の整数どうしで約 7 秒かかる. こうして, 整数どうしの積を掛け算とほぼ同じ時間に抑える. 分数との積の gcd は二乗の時間がかかるので, 分数の冪の予算は広げない.
- 同時に動く数: 1 つの process の中で同時に動く検算は CPU の数までとする. 期限を過ぎた検算も, 止まるまで枠を持ち続ける. 新しい検算は枠が空くのを待ち, その待ち時間も自分の締切に含める. したがって, 期限を過ぎた検算が占める thread は CPU の数を超えない.

## 結果

- 3 つの backend で `wall_seconds` の意味が同じになった. 検算に時間の掛かるジョブは, 以前は成功していたものが `TIMEOUT` になりうる.
- 検算が枠を持ったまま止まらない場合, 後のジョブの検算が枠を待って `TIMEOUT` になりうる. 区切りの間の 1 回の積が長い入力では, この待ちが起こる.
- 第三者の backend は `ExecutionContext.deadline` を使えば同じ契約になる. 使わなくても, 締切の後の成功は `TIMEOUT` になり, 締切から 5 秒で打ち切られる.

## 確認

- 単体試験 (`algebramesh-core`): CAS がすぐ答え検算が長い backend が `TIMEOUT` になり, 検算が次の区切りで止まること. 締切の後に成功を返す backend が `TIMEOUT` になること. 締切を無視する backend が締切の 5 秒後に打ち切られること. 締切の前に終わる検算と, 取り消された検算.
- 各 backend の既存の単体試験と結合試験 (検算は `check_result` を通る).
