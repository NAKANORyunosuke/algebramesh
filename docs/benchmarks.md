# 性能測定

設計書 §13.2 の性能評価のうち, 独立なジョブを worker 数を変えて実行した結果を記録する.
単一ジョブの高速化は扱わない. 一律な線形高速化は合格条件ではない.

## 方法

```bash
sh tests/bench/run-bench.sh "1 2 4" 16 28
```

- worker: 1 slot の Asir agent を 1, 2, 4 台 (`compose.cluster.yml` の `bench-worker` を `--scale` で増やす).
- ジョブ: `(x+y+z+1)^28 (x-y+2z+3)^28` を展開した多項式 (31,465 項, 約 2.4 MB の JSON) の `polynomial.factor` を 16 件. 各ジョブで積の検算まで行う.
- 時間: 1件目の投入から16件目の完了確認までの経過時間. 投入と待機は CLI を `docker exec` で1件ずつ順に呼ぶ.

## 結果 (2026-11-03)

環境: Windows 11 上の Docker Desktop (WSL2), Docker から見える CPU 18, メモリ 47 GiB.
scheduler, worker, client はすべて同じマシンのコンテナである.

| worker 数 | 所要時間 (秒) | ジョブ/秒 | 1 worker との比 |
|---|---|---|---|
| 1 | 45.9 | 0.35 | 1.00 |
| 2 | 25.2 | 0.63 | 1.82 |
| 4 | 18.7 | 0.85 | 2.45 |

## 解釈

- 2 worker でほぼ倍になる. 4 worker では伸びが鈍る.
- 要因の候補:
  - CLI による逐次の投入と待機. 1回あたり数百ミリ秒かかる.
  - 1ジョブあたり約 2.4 MB の仕様と記録の転送.
  - 同じマシン上での CPU とメモリ帯域の共有.
- 物理的に別のホストでの測定, 8 worker, worker 故障時の回復時間, 通信量の測定はまだ行っていない (設計書 §13.2).
